# Development Workflow

## Source of truth

GitHub issues define implementation scope.

Before changing code:

1. Read the current GitHub issue and its acceptance criteria.
2. Inspect the existing repository and relevant documentation.
3. Propose a concise implementation plan.
4. Do not start implementation until the requested scope is clear.

Do not introduce functionality that belongs to a future issue or milestone.

## Branching

Use one branch per issue.

Preferred naming:

`<type>/<issue-number>-<short-description>`

Examples:

`feat/2-fastapi-foundation`

`test/3-api-tests`

`chore/4-code-quality`

Never implement issue work directly on `main`.

## Implementation

Keep changes focused on the current issue.

Avoid:

- unrelated refactoring
- speculative abstractions
- future milestone functionality
- unnecessary dependencies
- changes that are not required by the issue

Prefer small, readable, understandable changes.

If the implementation requires a design decision not covered by the issue,
stop and raise the decision before expanding the scope.

## Verification

Verification happens in two separate stages.

### 1. Specification review

First review the implementation against the GitHub issue.

Verify:

- every acceptance criterion is satisfied
- required functionality is present
- out-of-scope functionality was not introduced
- dependencies added are necessary for the issue
- changed files are relevant to the issue
- documentation matches the actual implementation
- no future milestone functionality was implemented accidentally

The specification review answers:

`Did we build exactly what the issue asked for?`

Do not proceed to final completion if the specification review fails.

### 2. Code review

After specification compliance is confirmed, review the implementation itself.

When a code-review skill is available, use it for this stage.

Keep specification compliance and code-quality review separate.

Review for:

- correctness
- readability
- maintainability
- unnecessary complexity
- duplicated logic
- error handling
- typing
- security concerns
- dependency usage
- test quality
- consistency with the existing codebase

The code review answers:

`Is the implementation itself good engineering?`

Address relevant findings before completing the issue.

## Required checks

Run every automated check required by the current issue.

Do not claim completion when required checks fail.

Later milestones may require checks such as:

`uv run pytest`

`uv run ruff check .`

`uv run ruff format --check .`

`uv run mypy app`

Only run checks that exist in the repository or are required by the issue.

## Git

Do not commit directly to `main`.

Use clear conventional-style commit messages where practical.

Examples:

`feat: add FastAPI application foundation`

`test: add health endpoint tests`

`chore: configure Ruff and mypy`

Commit messages must describe the change only.

Do not include:

- AI or assistant attribution
- Claude references
- `Generated by Claude`
- `Created with Claude`
- `Co-authored-by` entries referring to Claude or another AI tool
- signatures, footers, or metadata identifying an AI coding tool

## Pull requests

Before opening a pull request:

1. Review the complete diff.
2. Complete the specification review.
3. Complete the code review.
4. Run all checks required by the issue.
5. Verify all acceptance criteria.

The pull request description should contain:

- a concise summary of the change
- the main implementation details
- verification performed
- `Closes #<issue-number>`

Use `Closes #<issue-number>` rather than only referencing the issue so GitHub automatically closes the related issue when the pull request is merged.

Example:

`Closes #2`

Pull request titles and descriptions must not contain AI or assistant attribution.

Do not include:

- Claude references
- `Generated by Claude`
- `Created with Claude`
- AI-generated signatures or footers
- any wording indicating which AI coding tool assisted with the implementation

The pull request should read like a normal engineering contribution.

## Merge

Merge only when:

- the issue specification is satisfied
- code review findings are resolved
- required checks pass
- CI passes when CI is available
- the pull request contains the appropriate `Closes #...` reference

After merge, verify that the related GitHub issue was closed.
