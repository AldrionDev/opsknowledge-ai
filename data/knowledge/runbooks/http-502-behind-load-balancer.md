# HTTP 502 Errors Behind a Load Balancer

## Overview

An HTTP `502 Bad Gateway` response is generated by a gateway or proxy, here a layer 7 load balancer, when it receives an invalid response from the upstream server or cannot get a response at all because the connection to the upstream failed. The client sees the error, but the cause is almost always between the load balancer and the backend, not in the client request.

Do not confuse 502 with its neighbours:

- `503 Service Unavailable`: the load balancer has no healthy backend to send the request to, or the backend is deliberately refusing traffic.
- `504 Gateway Timeout`: the connection to the backend worked, but the backend did not answer within the load balancer timeout. This is a slow-response problem, not a broken-connection problem.
- `502`: the connection to the backend was refused, reset, closed early, or the response was malformed.

Common causes of 502 errors:

- **Backend crashed, restarting, or not yet listening.** Containers in `CrashLoopBackOff`, `OOMKilled` pods, or a rollout that sends traffic to pods that are not ready.
- **Keep-alive timeout mismatch.** The load balancer reuses a persistent connection that the backend has already closed. This can happen when the backend keep-alive (idle) timeout is shorter than the load balancer idle timeout. The backend may close an idle connection after its short timeout while the load balancer still considers the connection open. If the load balancer then sends a request on that connection, the request can fail with a connection reset or an empty response, which the load balancer may report as 502. The outcome is not certain for every idle connection: the failure only occurs when a request is sent on a connection that the backend has already closed or is closing. Depending on timing and on the retry behavior of the load balancer, the same configuration can also produce successful requests, so the errors are typically intermittent and tend to appear after idle periods.
- **Protocol or port mismatch.** The load balancer speaks HTTPS to a plain-HTTP backend, or the target group points at the wrong port.
- **Malformed or oversized response.** Invalid HTTP headers, response headers larger than the limit, or a backend that closes the connection before sending the full body.
- **Backend worker saturation.** All worker processes or threads are busy and the backend resets new connections.
- **Network problems.** Security group or network policy changes, or an exhausted connection tracking table.

This runbook uses a Kubernetes service behind a managed cloud layer 7 load balancer as the example, but the diagnostic logic applies to any load balancer or reverse proxy.

Command conventions used in this runbook:

- **Read-only** commands only inspect state and are safe to run at any time.
- **Changes state** commands modify configuration, workloads, or cluster resources.
- **Destructive** commands delete or discard data and need an explicit check of the target first.

## Symptoms

- Clients receive `502 Bad Gateway`, either on a fraction of requests or on all of them.
- The 5xx rate on the load balancer increases while backend application logs show few or no errors for the failing requests, because the requests never reached the application.
- Errors are intermittent and appear at low traffic or after idle periods. This pattern suggests a keep-alive mismatch.
- Errors appear during deployments or correlate with pod restarts. This pattern suggests backends that are not ready or are crashing.
- The load balancer access log shows status `502` together with a missing, `-`, or zero backend status code, which indicates that no valid backend response was received.
- The backend target health shows unhealthy or draining targets.

## Diagnosis

All commands in this section are **read-only**, with one exception: step 5 creates a short-lived test pod and is labeled accordingly. Replace `<namespace>`, `<service>`, and `<deployment>` with the values for the affected workload.

1. Determine the scope. Check which routes, hosts, and backends are affected, since when, and whether the rate is constant or intermittent. Compare the load balancer 5xx metric with the backend request count and with the backend 5xx metric. If the load balancer reports many more 502 responses than the backend reports errors, the requests are failing before they reach the application.

2. Inspect the load balancer access log for the failing requests. Compare the status returned to the client with the status returned by the backend. A 502 without a backend status means that the connection failed or the response was invalid. Note the timing fields: a failure after a long idle period or a reset right after the connection is established helps to separate the causes.

3. Check target health in the load balancer and the endpoints behind the Kubernetes Service.

   ```bash
   kubectl get endpoints <service> -n <namespace>
   kubectl get pods -n <namespace> -l app=<label> -o wide
   ```

   Missing endpoints mean that no pods are ready. Pods with a high restart count or a status of `CrashLoopBackOff` or `OOMKilled` point to the Kubernetes CrashLoopBackOff runbook.

4. Check recent pod restarts, readiness, and rollout activity.

   ```bash
   kubectl get events -n <namespace> --sort-by=.lastTimestamp
   kubectl rollout status deployment/<deployment> -n <namespace>
   kubectl describe pod <pod> -n <namespace>
   ```

   If the 502 spikes line up in time with pod terminations or restarts, requests are being sent to pods that are shutting down or not ready.

5. Test the backend directly, bypassing the load balancer, from a pod in the cluster. Use the pod IP or the Service name. **Changes state:** the command creates a temporary pod, which `--rm` removes when the command ends. Only the request itself is read-only.

   ```bash
   kubectl run curl-test --rm -it --restart=Never --image=<curl-image> -n <namespace> -- \
     curl -sv http://<service>.<namespace>.svc.cluster.local:8080/healthz
   ```

   A failure or reset when calling the backend directly shows that the backend is the problem. A clean response shows that the problem is in the load balancer configuration or in connection reuse.

6. Compare the keep-alive settings. Find the load balancer idle timeout (for example 60 seconds) and the backend keep-alive timeout. Examples of backend settings:

   - Node.js HTTP server: `server.keepAliveTimeout` (default 5 seconds) and `server.headersTimeout`
   - nginx: `keepalive_timeout` (default 75 seconds)
   - gunicorn: `--keep-alive` (default 2 seconds)

   If the backend keep-alive timeout is shorter than the load balancer idle timeout, a connection may be closed by the backend before, or at the same moment as, the load balancer reuses it. This is a possible explanation for intermittent 502 responses that are not correlated with deployments and are not visible in the application logs. A mismatch alone does not prove the cause: confirm it by correlating failures with idle gaps on the connection, with the absence of a backend status code, and with a connection close or reset on the backend side.

7. Check the protocol and port. Confirm that the load balancer target protocol (HTTP or HTTPS) and port match what the container listens on, and that the health check path returns `200`.

8. Check resource saturation of the backend. Look at CPU throttling, memory, worker utilization, and connection counts during the error window. A saturated backend can reset new connections or fail health checks.

9. Check for recent changes: a new release, a configuration change on the proxy or application server, a changed idle timeout on the load balancer, a network policy or security group change, or a certificate rotation.

## Resolution

Choose the branch that matches the cause found during diagnosis.

### Keep-alive timeout mismatch

The backend keep-alive timeout must be **longer** than the load balancer idle timeout, so the load balancer is always the side that closes an idle connection first.

1. Increase the backend keep-alive timeout above the load balancer idle timeout, with a margin of a few seconds. **Changes state:** this requires a configuration change and a rolling restart of the backend.

   Node.js:

   ```javascript
   server.keepAliveTimeout = 65000; // load balancer idle timeout is 60 s
   server.headersTimeout = 66000;   // must be greater than keepAliveTimeout
   ```

   nginx:

   ```text
   keepalive_timeout 65s;
   ```

2. Apply the change through the normal release process and restart the workload with a rolling update. **Changes state:**

   ```bash
   kubectl rollout restart deployment/<deployment> -n <namespace>
   ```

3. Do not fix this by lowering the load balancer idle timeout below the backend timeout without checking other clients of the same load balancer, because it changes the behavior for every target behind it. If it is changed anyway, treat it as **Changes state** for every service behind that load balancer.

### Backend crashing or not ready

1. Use the Kubernetes CrashLoopBackOff runbook to find and fix the cause of the restarts, for example an `OOMKilled` container with a too-low memory limit.
2. Make sure that the readiness probe reflects the ability to serve traffic, so that pods are added to the endpoints only when ready. **Changes state:** this is a change to the pod template and triggers a rolling update.
3. Add a `preStop` delay and a sufficient `terminationGracePeriodSeconds` so that a terminating pod is removed from the load balancer before it stops accepting connections. **Changes state:**

   ```yaml
   lifecycle:
     preStop:
       exec:
         command: ["sleep", "10"]
   ```

   The `sleep` command must exist in the container image. Set `terminationGracePeriodSeconds` (default 30) higher than the `preStop` delay plus the time the application needs to shut down gracefully.

4. To stop the impact while the cause is being fixed, roll back to the previous release. **Changes state:**

   ```bash
   kubectl rollout undo deployment/<deployment> -n <namespace>
   ```

### Protocol, port, or health check mismatch

1. Correct the target port, the target protocol, or the health check path in the load balancer or ingress configuration so that it matches the container. **Changes state.**
2. Roll back the configuration change that introduced the mismatch if it is recent. **Changes state.**

### Malformed or oversized responses, and saturation

1. For header size errors, reduce the size of cookies or headers set by the application, or raise the limit in the backend server. **Changes state.**
2. For saturation, scale out the workload or increase the worker count. **Changes state:**

   ```bash
   kubectl scale deployment/<deployment> -n <namespace> --replicas=<count>
   ```

   Confirm that the nodes have capacity for the additional replicas, and that downstream dependencies such as the database connection limit can handle the extra load.

## Verification

All commands in this section are **read-only**.

1. The load balancer 502 and 5xx rates return to the normal baseline and stay there. For an intermittent cause such as a keep-alive mismatch, observe for at least several idle timeout periods and during both low and high traffic, since the errors may only appear in specific traffic patterns.
2. All targets are healthy and the endpoints list contains every expected pod.

   ```bash
   kubectl get endpoints <service> -n <namespace>
   kubectl get pods -n <namespace> -l app=<label>
   ```

3. A direct request to the service through the load balancer returns the expected status.

   ```bash
   curl -sS -o /dev/null -w '%{http_code}\n' https://app.example.com/healthz
   ```

4. The load balancer access log shows a backend status code for every request, and no `502` entries without a backend status.
5. The backend pods run without new restarts.

   ```bash
   kubectl get pods -n <namespace> -l app=<label> -o wide
   ```

6. Confirm that the configured backend keep-alive timeout is longer than the load balancer idle timeout, and record both values in the service documentation.
